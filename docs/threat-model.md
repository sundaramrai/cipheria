# Cipheria security boundaries

This describes the current implementation, not a security certification. Scope: the same-origin Next.js/FastAPI application, PostgreSQL, Redis, and downloaded exports. See [architecture](architecture.md) for the stored data and derivation format, and [roadmap](technical-roadmap.md) for unfinished work.

| Threat | Current controls | Remaining exposure |
| --- | --- | --- |
| Stolen database, Redis snapshot, or export | Vault payloads use browser-side AES-256-GCM; PBKDF2-SHA-256 uses 600,000 iterations and a random account salt. Verifiers are bcrypt-hashed; refresh tokens are stored hashed. | Item titles, categories, account details, counts and timestamps remain readable. Password guessing against ciphertext is possible offline. Existing exports require the original password and salt. |
| Stolen account session | Short-lived in-memory access tokens; HttpOnly refresh cookie; server-side session validation and revocation; master-verifier checks for sensitive operations. | A stolen session can retrieve ciphertext and metadata. Non-extractable keys do not prevent malicious code using an unlocked key. Revocation cannot erase previously downloaded data. |
| Cross-site request forgery | State-changing requests require `X-Requested-With: XMLHttpRequest`. Explicit origins must exactly match `ALLOWED_ORIGINS`; cross-site Fetch Metadata without Origin is rejected. CORS allows only configured origins. Refresh cookies are host-only, HttpOnly, `SameSite=Lax`, and Secure in production. | An allowed origin must be trusted. Non-browser clients can omit Origin but must send the custom header; this header is not authentication. Browser deployments across different sites are unsupported. |
| Injected browser code | Per-request nonce CSP authorizes application scripts, blocks unnonced inline scripts, disallows objects and framing, and restricts connections. API responses are `no-store`; document responses prevent shared caching. | Styles still allow inline CSS. `strict-dynamic` trusts scripts loaded by trusted scripts. A compromised deployment, dependency, extension, or origin can steal secrets during unlock. CSP is defense in depth. |
| Stolen device or malicious extension | Keys are held in memory and locking removes application-held decrypted state; access tokens are not persisted to Web Storage. | An unlocked browser, clipboard, screenshots, operating-system access, extensions, and plaintext browser CSV exports remain outside these protections. Delete CSV exports after importing. |
| Tampered/replayed records or concurrent writes | AES-GCM rejects altered payloads. Version 2 AAD binds vault/item/key IDs. Imports use transactions and retry receipts. Item revisions and If-Match reject stale writes; a shared account lock coordinates migrations and rewrapping with edits. Full key migrations verify every source revision; old-salt writes are rejected. | Legacy ciphertext has no item-context AAD until upgraded. The API cannot prove an opaque ciphertext uses the claimed key, and these controls cannot detect rollback by a malicious server. Rewrapping alone cannot revoke a previously copied data key; explicit key rotation changes that key. |
| Forgotten password, old backups, service loss | Existing JSON exports can be decrypted locally and re-encrypted for another account with the source password. | No passwordless recovery or independent portable-backup key exists. Changing a live password cannot revoke old exported copies. Backups require separate safe storage. |

## Deployment contract

Serve the browser and `/api` through the same HTTPS origin. Set `ENVIRONMENT=production` explicitly and configure `ALLOWED_ORIGINS` with complete origins, for example `https://cipheria.vercel.app`; wildcards, credentials, and URL paths are rejected. Explicitly list any trusted preview origin. Do not derive trust from Host or forwarded headers. Direct API scripts must send the custom request header for POST/PATCH/DELETE as well as their normal credentials.

Nonce CSP requires dynamic document rendering, including the landing page, and removes static document caching. Next.js receives the policy on the internal request so its own scripts receive the nonce; the theme script also receives it. Keep static asset caching separate. Set `CSP_REPORT_ONLY=1` to inspect browser console violations during staging; there is no reporting collector. Enforcement is the default. Do not enable a report collector that records vault URLs, payloads, or secrets without a separate privacy review. Production connections allow same-origin APIs and the explicit HIBP range check; development additionally permits HMR connections.

Email verification bodies and tokens are not logged when SMTP is absent. Avoid enabling SQL parameter logging or browser traces for real accounts. Test fixtures and CI use disposable accounts and a local isolated database, with screenshots, videos and traces disabled.

## Evidence and limits

Backend regression tests cover request-origin/header rejection before database access, preflight, refresh-cookie expiry on failure, production cookie attributes, token-safe mail logging, import atomicity, ownership and PostgreSQL locking. Browser tests cover nonce enforcement, client navigation, authentication, locked reload/unlock, item operations, CSV/JSON import/export, and session revocation. CI runs lint, typecheck, unit/integration tests, migrations on a disposable database, a production build and Chromium checks. A locally passing workflow does not demonstrate production configuration or replace an independent security review.

Design references: [OWASP CSRF guidance](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html), [Next.js nonce CSP and rendering requirements](https://nextjs.org/docs/app/guides/content-security-policy).
